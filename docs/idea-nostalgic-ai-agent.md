# 创意三：基于 AI 的「怀旧导航」代理（Nostalgic AI Agent）

## 一、概念复述与留存逻辑

- **核心功能**：在页面角落出现一个 90 年代风格的 3D 助手（类似 Office 助手 Clippy，但更酷）。它不仅是视觉装饰，还是一个 **RAG 助手**，能根据用户**收藏的书签**回答问题，并用 **90 年代的语气**和用户交流。
- **留存逻辑**：将**工具属性**转化为**情感陪伴**属性。AI 助手会根据用户的浏览习惯「成长」，让用户产生情感连接。

---

## 二、与现有留存分析的对应关系

在《deep-analysis-retention-root-causes》里，我们得到：

- 当前产品主要满足的是「尝鲜」→ 任务有自然终点，容易卸。
- 要留存，需要创造**新的、可重复的「工作」**，或强化**身份/归属**。

| 维度 | 怀旧 AI 代理能贡献什么 |
|------|------------------------|
| **新「工作」** | 「和助手聊一聊」「问它我收藏里有什么」「让它用 90s 口吻总结」→ 可重复、有理由多次打开。 |
| **情感陪伴** | 固定角色 + 90s 人格 + 根据「我的书签/习惯」给回复 → 从「用工具」变成「有个伴」，卸载时会有「舍不得」感。 |
| **身份/表达** | 「我的复古小助手」成为用户自我认同的一部分；若可分享助手金句或对话，还能形成社交表达。 |
| **每日触点** | 助手常驻页面角落（或新标签页），每次浏览都有机会看到、点开、说一句 → 习惯回路有 Cue。 |

因此，这个创意**直接对准根因 B**（触达了但任务一次性）：用「陪伴 + 成长」制造持续理由和情感连接，是合理的战略方向。

## 三、功能拆解与「成长」的具体含义

### 3.1 功能模块

| 模块 | 含义 | 说明 |
|------|------|------|
| **角色呈现** | 90s 风格 3D 助手（Clippy-like） | 出现在页面角落或新标签页；可动、可点、有气泡/对话框。 |
| **RAG 能力** | 基于书签回答问题 | 索引书签（标题、URL、文件夹）；用户问「我存过什么关于 React 的？」时，用书签作为上下文让 LLM 回答。 |
| **90s 语气** | 人格与话术 | 用 system prompt 或 few-shot 约束：复古用语、老式客气、梗（「您有一封新邮件」式调侃等）。 |
| **「成长」** | 随使用产生变化 | 见下。 |

### 3.2 「根据浏览习惯成长」可以怎么做（不越界、可落地）

若完全本地、无后端，「成长」只能基于**扩展内可获取的数据**和**本地存储**：

- **基于书签**：书签数量、文件夹结构、最近添加的书签 → 助手可以说「您最近收藏了不少设计类网站哦」「您的书签已经突破 100 个啦」，让用户觉得「它了解我」。  
- **基于对话历史**：在本地存最近 N 轮对话（chrome.storage.local），下次打开时可以说「上次您问过那个博客，需要再帮您找找吗？」→ **记忆感**。  
- **基于使用频率**：例如「您这周已经和我聊了 5 次啦」→ 轻量「陪伴统计」，增强归属感。  
- **不做的（隐私/复杂度）**：不读浏览历史正文、不上传书签到服务器；若用云端 LLM，只传**用户当前问题 + 检索到的少量书签文本**，不传全量书签。

这样「成长」= **助手对「我的书签 + 和我的对话」有记忆、会引用、会调侃**，而不是真正的模型微调或复杂行为树。

## 四、技术选项与约束

### 4.1 书签 RAG（本地即可）

- **数据来源**：`chrome.bookmarks` API（标题、URL、folder 名）。  
- **索引**：可在扩展内建轻量「索引」（例如标题 + URL 的列表或简单 embedding）。不需要后端；可选：用浏览器侧或本地 Worker 跑小模型做 embedding，或只用关键词/标题匹配做检索。  
- **检索**：用户提问 → 用问题在书签标题/URL/文件夹名里做匹配或向量检索 → 取 Top-K 条作为上下文交给 LLM。

### 4.2 LLM 从哪来

| 方案 | 优点 | 缺点 | 与「无后端」的关系 |
|------|------|------|---------------------|
| **第三方 LLM API**（OpenAI / Claude / 国内大模型等） | 实现快、效果可控、易做 90s 语气 | 需 API Key；请求走外网；有成本；书签摘要/问题会发到云端 | 不建自己的后端，但依赖外部 API |
| **本地模型**（如 WebLLM、Ollama + 扩展通信） | 数据不出设备、无持续 API 成本 | 体积与算力要求高；在扩展里集成复杂 | 完全符合「无后端、本地」 |
| **规则/模板 + 无 LLM** | 零依赖、无隐私顾虑 | 无法真正「根据问题答」，只能预设话术 + 书签列表填空 | 可做 MVP 演示「氛围」，不能算真 RAG |

建议：**首版用 API 验证概念和留存**；若验证成功再考虑「可选本地模型」或「仅本地规则版」给隐私敏感用户。

### 4.3 助手 UI 放在哪

- **方案 A**：**内容脚本注入** → 在任意网页角落挂一个小窗 + 助手形象。优点：每次浏览都能见到；缺点：和现有 Y2K 注入一样要处理各种站点兼容、可能被站点 CSP 限制。  
- **方案 B**：**新标签页** → 新标签页 = Y2K 首页 + 助手。优点：体验可控、无站点干扰；缺点：只有开新标签时才能见。  
- **方案 C**：**A + B** → 新标签页有完整助手；其他页可有一个小入口（如图标）点开弹层与助手对话。  

从留存和实现成本折中，可先做 **B 或 C**，避免一开始就做全站注入的复杂度和审核风险。

### 4.4 记忆与「成长」的存储

- **全部用 `chrome.storage.local`**：对话历史（截断到最近 N 条）、上次提到过的书签、简单统计（如「本周对话次数」）。  
- 不建后端 = 不做跨设备同步；单机「成长」足够支撑情感连接。

## 五、MVP 与分阶段落地

| 阶段 | 目标 | 可做内容 |
|------|------|----------|
| **MVP（验证反应）** | 验证用户是否愿意和「复古助手」对话 | 固定 90s 形象 + 简单气泡 UI；**不做真 RAG**，只做几条预设回复（如「您今天看起来不错！」「需要我帮您看看书签吗？」）+ 一个「从书签里随机推荐一个」的按钮，用 `chrome.bookmarks` 读本地书签。 |
| **V1（真 RAG + 90s 语气）** | 书签问答 + 人格化 | 书签索引（标题/URL）+ 用户问题 → 检索 Top-K → 调 LLM API，system prompt 约束 90s 语气；回答仅基于书签，不瞎编。 |
| **V2（成长感）** | 情感连接 | 存对话历史与简单统计；助手在开场或回复里引用「上次您问过…」「您这周常来哦」等。 |

先上 MVP 可以**不依赖任何 API、不涉及隐私**，只验证「有一个 Clippy 一样的复古角色跟我说话」是否有吸引力；再决定是否投入 RAG + API。

## 六、风险与设计注意

| 风险 | 缓解思路 |
|------|----------|
| **隐私**：书签/对话上传 | 明确文案「仅用书签标题/URL 作为问题上下文」；若用 API，可选项「仅本地模式（无 AI）」或后续支持本地模型。 |
| **成本**：API 按量付费 | 限制每用户每日请求次数；或先做「书签检索 + 模板回复」减少调用；或仅在新标签页提供助手以控制使用场景。 |
| **「 creepy」感** | 「成长」只限于书签与对话的正面引用，不评价用户、不过度主动打扰；语气轻松、怀旧、带梗，避免像监控。 |
| **复杂度** | 严格按阶段：先形象+预设话术，再 RAG，再记忆/成长。 |

---

## 七、一句话小结

**怀旧导航代理**把 Y2K-ifier 从「一次性视觉玩具」升级为**有陪伴感、可重复使用、且与用户书签/习惯绑定的 RAG 助手**，和深度分析里的「根因 B + 身份/情感」高度一致。技术上：书签 RAG 可全本地；LLM 首版用 API 可行，后续可探索本地模型；「成长」用本地存储的对话与简单统计即可。建议先做**无 API 的 MVP**（复古形象 + 预设话术 + 书签随机推荐）验证用户是否买账，再上真 RAG 与成长逻辑。
